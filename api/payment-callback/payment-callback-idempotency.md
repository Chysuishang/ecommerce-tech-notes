# 支付回调接口：验签、幂等与状态收敛

> 本文属于 `api/` 方向，讨论第三方支付异步通知接口的契约设计与幂等边界。
> 文中标注 **Recommended Design** 或 **Example** 的部分是设计方案与示例代码，不代表某个已上线产品的既有实现。

## Problem

支付回调接口最容易被做错的地方不是验签，而是**幂等边界画在哪一层**。

一个看起来没问题的实现：

1. 收到通知 → 验签通过；
2. 调用订单服务："这笔订单支付成功了吗？" 没成功 → 置为已支付、扣库存、发货；
3. 应答渠道定义的成功报文。

问题出在第 2 步的判定对象。它判定的是**被支付对象的最终状态**，而不是**这次通知是否已经被处理过**。这两者在简单场景下常常等价，所以在测试环境里看不出问题，一到真实流量就暴露：

- **充值场景。** 订单状态可能已经是"已支付"，但"用户余额 +100、写一条充值流水"这两步的幂等性由谁保证？如果重投发生在这两步之间，就会再加一次。
- **合并支付。** 一笔渠道支付对应多个商城订单。订单 A 已支付，不代表订单 B 已支付。用"订单状态"做短路，会把整笔支付的剩余部分吞掉。
- **部分失败。** 加余额成功、写流水失败，事务边界没罩住这两步，重投时就会双写。

所以正确的判定对象是**本次通知对应的支付流水记录**，不是被支付的对象。本文只讨论回调这一层的接口契约与幂等设计，不讨论渠道 SDK 的接入细节。

## Business Scenario

商城系统里需要处理回调的支付场景，幂等难点各不相同：

| 场景 | 渠道支付单与商城对象的关系 | 幂等难点 |
| --- | --- | --- |
| 订单支付 | 1 笔支付 → 1 个订单 | 订单支付结果、库存、发货计划 |
| 合并支付 | 1 笔支付 → N 个订单 | 每个订单独立收敛，不能整体短路 |
| 余额充值 | 1 笔支付 → 1 次入账 | 入账流水本身必须唯一 |
| 线下/对公转账 | 1 笔入账 → 需人工确认 | 回调带的信息不足以自动判断 |

四类场景有一个共同点：**回调只负责"把支付结果落到本地"，不负责"向用户展示成功"**。用户看到的支付成功页来自同步返回，而同步返回是不可信的——用户可能在同步返回到达之前就关掉页面，也可能渠道扣款成功但同步返回因网络原因丢失。因此回调必须能在用户早已离开的情况下独立完成收敛。

## Why It Happens

### 渠道只提供 at-least-once

主流支付渠道的异步通知机制都是"至少一次投递"：商户需要在规定时间内返回渠道定义的成功应答，否则渠道按退避策略重试，并持续较长时间。这直接推出一个结论——**"业务处理成功但应答丢失"是必然事件，不是异常事件**：

```
T0  渠道发起第 1 次通知
T1  本地事务提交成功（余额已加、流水已写、状态已改）
T2  进程在写应答之前被重启 / 网关超时切断了连接 / 上游限流把响应丢了
T3  渠道认为失败，按退避策略发起第 2 次通知
```

第 2 次通知到达时，本地状态已经是"处理完成"。此时幂等判断写错，就会重复入账；判断写对，就应该直接应答成功且不做任何副作用。

### 三个常见错误做法

**1. 用分布式锁当正确性保证。**
锁能减少并发冲突，但不能替代数据库层面的唯一性约束。锁的持有时间、过期时间、多实例时钟漂移、Redis 故障切换，每一个都会让锁失效。锁失效之后，问题只是从"每次都错"变成"偶发地错"——而偶发错误比稳定错误更难排查。

**2. 先应答成功再处理业务。**
好处是绝不重复投递，代价是处理失败就永久丢单。除非同时补一条本地落库 + 定时补偿链路，否则这条路比幂等本身更贵。

**3. 幂等判断写在事务外。**
两个并发通知同时查到"未处理"，然后都进入处理分支。如果表上没有唯一索引兜底，就真的会双写。正确的写法是把判定做成一条带条件的更新语句，让数据库的行级锁来裁决。

## Design

（**Recommended Design**：以下为设计建议，不代表任何已上线产品的既有行为）

把回调接口拆成三层，每层职责单一，不要互相代替。

### 第 1 层：验签与解密（拒绝伪造，但不丢单）

- 用渠道平台证书验签、解密；验证失败**不做任何业务处理**。
- 关键：验签失败的应答**不能是成功应答**。如果对伪造报文和对真实报文都回成功，看起来"更安全"，实际上会让渠道停止重投真正的那笔支付，导致的丢单无法挽回。
- 记录原始报文的摘要与失败原因（不要整段落盘，见 Practical Notes）。

### 第 2 层：幂等落库（以数据库唯一约束为真相）

幂等键的选择：

```
idempotency_key = deposit_no（商城支付单号） + deposit_trade_no（渠道交易号）
```

只用商城单号不够：用户关掉收银台再重新支付，同一商户单号可能出现两条不同的渠道交易。只用渠道交易号也不够：撤销、退款会带来同一交易号下的多条通知。两者组合才能既覆盖"同一单重复通知"，又覆盖"同单多次支付"。

落库阶段用**唯一索引 + 冲突即视为重复**：

```sql
-- Example: 幂等索引
UNIQUE KEY `uk_deposit_no_trade_no` (`deposit_no`, `deposit_trade_no`)
```

并发首次通知时，其中一个事务会拿到 duplicate key 错误。把这个错误当作"重复通知"处理，而不是当作失败向上抛——抛上去会导致渠道重投，重投还是同一个冲突，形成无意义的循环。

### 第 3 层：状态跃迁（副作用只发生在一次跃迁里）

支付流水上挂一个处理状态，例如：

```
0  默认（已落库，业务副作用尚未执行）
1  接收正确、数据处理完成
9  异常订单（金额不符、单据缺失，需要人工介入）
```

副作用与状态变更放进**同一个数据库事务**，并用条件更新做 CAS：

```sql
-- Example: 只有 0 -> 1 的那一次会 affected = 1
UPDATE consume_deposit
   SET deposit_state       = 1,
       deposit_trade_status = ?,
       deposit_notify_time  = ?
 WHERE deposit_id = ?
   AND deposit_state = 0;
```

- `affected = 1`：本次通知是**首次处理**，继续执行加余额、写流水、推进订单；
- `affected = 0`：说明已经处理过（或状态是 9），**直接应答成功**，不做任何副作用。

这个写法的价值在于：幂等的真相来源是数据库的行级竞争结果，而不是应用层的"先查后写"。多实例、重启、并发、锁失效都不会破坏它。

### Flow

```
渠道通知
  │
  ├─ 验签/解密失败 ──► 记录摘要 + 告警 ──► 返回非成功应答（让渠道重投）
  │
  ▼ 验签通过
幂等落库（UNIQUE 冲突 => 视为已有记录）
  │
  ▼
CAS: deposit_state 0 -> 1
  │
  ├─ affected = 0 ──► 返回成功应答（重复通知，无副作用）
  │
  ▼ affected = 1（同一事务内继续）
加余额 / 写流水 / 更新订单支付结果 / 发领域事件
  │
  ├─ 全部成功 ──► 提交事务 ──► 返回成功应答
  └─ 任一步失败 ──► 回滚事务 ──► 返回失败应答（渠道重投，下次从 0 重新走）
```

注意最后一条分支：**事务回滚后状态仍然是 0**，所以重投时 CAS 依然能拿到 `affected = 1`，不会漏处理。这正是"先改状态再处理"与"处理完再改状态"的关键区别——后者在失败时会留下一个"状态已变但业务没做"的中间态，只能靠人工修数据。

## Data Model

支付流水表的核心字段（字段命名与状态取值参考文末来源，用于说明语义）：

| 字段 | 含义 | 在回调中的作用 |
| --- | --- | --- |
| `deposit_id` | 支付流水主键 | 行级 CAS 的对象 |
| `deposit_no` | 商城支付编号 | 幂等键之一 |
| `deposit_trade_no` | 渠道交易号 | 幂等键之一 |
| `order_id` | 关联订单号；合并支付时可能是逗号分隔的多个 | 决定要推进哪些订单 |
| `payment_channel_id` | 支付渠道 | 路由到对应的验签/解密逻辑 |
| `deposit_total_fee` | 交易金额 | 与本地支付单金额比对 |
| `deposit_payment_type` | 支付方式（在线支付 / 线下支付 / 信用支付等） | 决定副作用类型 |
| `deposit_state` | 处理状态 0 / 1 / 9 | 幂等与状态收敛 |
| `deposit_notify_time` | 渠道通知时间 | 排查重复投递的间隔 |
| `deposit_time` | 本地落库时间 | 对账基准 |

`order_id` 支持逗号分隔的多订单号，是为了合并支付：一笔渠道支付对应多个商城订单时，回调需要逐个推进，不能因为其中一个已完成就整体短路。

回调需要写入的渠道侧信息与本地状态要分开存放：`deposit_trade_no`、`deposit_trade_status`、`deposit_seller_id`、`deposit_buyer_id` 属于**渠道回传的事实**，不要覆盖本地计算出的金额与优惠；`deposit_state`、`deposit_time` 属于**本地的处理状态**。混在一起之后，对账时无法区分"渠道说的"和"我们算的"。

## Example

（**Example**：示意结构，非可直接运行的完整实现）

```go
func (c *callback) Handle(ctx context.Context, channel uint, body []byte) (ack Ack, err error) {
    notify, err := verifyAndDecrypt(ctx, channel, body) // 验签 + 解密
    if err != nil {
        logNotifyDigest(ctx, channel, body)             // 只记摘要，不记全文
        return Ack{}, err                               // 非成功应答，等渠道重投
    }

    outTradeNo := notify.OutTradeNo    // 商城支付单号
    tradeNo := notify.TransactionID    // 渠道交易号

    err = dao.ConsumeDeposit.Transaction(ctx, func(ctx context.Context, tx gdb.TX) error {
        // 1) 幂等落库：唯一索引冲突 => 已有记录，直接取回
        depositID, err := upsertDeposit(ctx, tx, outTradeNo, tradeNo, notify)
        if err != nil {
            return err
        }

        // 2) 金额比对：整数分比较，避免浮点误差
        if notify.AmountTotalCents != expectedCents(ctx, tx, outTradeNo) {
            return markAbnormal(ctx, tx, depositID)     // 置 9，转人工
        }

        // 3) CAS：0 -> 1，只有首次通知会拿到 1 行
        affected, err := casToProcessed(ctx, tx, depositID, notify)
        if err != nil {
            return err
        }
        if affected == 0 {
            return nil                                  // 重复通知，直接返回成功
        }

        // 4) 副作用，全部位于同一事务内
        if err = creditUserMoney(ctx, tx, outTradeNo, notify.AmountTotalCents); err != nil {
            return err
        }
        if err = appendConsumeRecord(ctx, tx, outTradeNo, notify); err != nil {
            return err
        }
        return advancePaidOrders(ctx, tx, outTradeNo)   // 合并支付时逐个推进
    })
    if err != nil {
        return Ack{}, err                               // 回滚；状态仍为 0，等渠道重投
    }
    return Ack{Code: "SUCCESS", Message: "成功"}, nil
}
```

要点：

- 第 4 步任何一步失败都让整个事务回滚，`deposit_state` 回到 0，重投时重新参与 CAS；
- `upsertDeposit` 必须在事务内完成，否则并发通知会各插一条；
- 应答体必须是渠道期望的结构，并且要**显式写回**。在基于框架的实现里，如果不清空框架已经准备好的响应缓冲就直接返回，渠道收到的可能是框架默认的错误结构，会被判定为处理失败并触发重投——这类问题在联调时几乎必然踩一次。

## Edge Cases

| 情况 | 现象 | 处理建议 |
| --- | --- | --- |
| 回调金额 ≠ 本地支付单金额 | 用户改价、渠道手续费、币种不一致 | 不推进订单，流水置 9 并告警；绝不允许"按回调金额入账" |
| 支付单查不到 | 回调先于本地落库提交到达 | 返回失败让渠道重投；连续重投仍失败则落异常表，由对账补偿 |
| 并发首次通知 | 两个通知同时到达 | 靠唯一索引兜住，冲突方按重复处理 |
| 合并支付部分完成 | 订单 A 已支付、B 未支付 | 逐个订单独立 CAS，不能用整笔支付的状态短路 |
| 订单已取消后又到账 | 用户取消后渠道延迟扣款 | 转入待退款队列，不得直接标记支付成功 |
| 订单超时关闭后到账 | 未支付关单，钱却到了 | 同上：转退款，不能重新打开已关闭的订单 |
| 状态为 9 的通知反复重投 | 每次都被判异常 | 异常单要有独立的幂等处理，避免无限重投与重复告警 |
| 验签失败但确实是真实通知 | 平台证书轮换、证书缓存过期 | 记录摘要并告警；证书问题在渠道重投窗口内会自动恢复，不要手工造单 |
| 通知乱序 | 撤销通知早于支付成功通知 | 状态机只允许 0→1，不允许 1→0；撤销走独立的退款单据 |
| 处理耗时超过渠道超时 | 规定时间内没返回应答 | 建议快速落库 + 异步推进业务，但必须保证"已应答成功"的结果最终一定被执行 |

## Practical Notes

**幂等记录的保留期。** 至少要覆盖渠道的最大重投窗口加上一个完整对账周期。清理太早，一笔迟到很久的通知会被当成首次处理，等于把幂等做废。

**金额类型。** 参考实现中支付流水的金额字段是浮点类型，属于历史包袱。新项目建议用整数分，或明确的 `DECIMAL(18,2)`，并在代码里统一用 decimal 库做除法与比较。用浮点数做金额相等判断，`99.99 != 99.99` 这类问题迟早会出现，而且往往出现在对账环节，而不是下单环节。

**不要把 Redis 锁当护城河。** 锁可以作为减少数据库竞争的优化，但幂等必须由唯一索引 + 状态跃迁保证。反过来，如果数据库幂等已经做对，锁通常不是必需品。把这句话倒过来执行——先上锁，指望它解决重复入账——是这类线上事故最常见的成因。

**日志。** 记录：支付单号、渠道交易号、通知次数、当前状态、处理结果、耗时。不要记录完整报文：里面有买家标识、商户号、金额，落盘日志属于数据泄露面。排查需要时用摘要比对。

**回调接口的鉴权定位。** 它是公开可达端点，必须绕过登录态鉴权，但要配独立的验签、限流与来源校验。不要因为"它不需要登录"就把它塞进业务接口的鉴权白名单里，那会把整个白名单的可信度拉低。

**幂等与会话无关。** 回调处理不能依赖任何用户会话、购物车、缓存中的临时状态，只能依赖数据库里已提交的事实。否则进程重启、缓存击穿都会让回调无法收敛。

**对账仍然要做。** 回调保证的是最终一致，不是"绝不漏单"。每天拉渠道账单与本地支付流水做双向比对：本地有渠道无，可能是伪造或本地误标；渠道有本地无，是真丢单，必须补。回调幂等做对了，也不能省掉这一步——它们解决的是两个不同的问题。

**顺序相关的一个细节。** 如果业务侧要用领域事件（如"支付成功"消息）驱动下游，事件必须发在事务提交之后（本地消息表 / 事务提交后投递），否则可能出现"下游收到消息但主库回滚"的幻影事件。这类问题排查成本极高，因为日志里每一条看起来都是对的。

## Summary

- 回调是"至少一次"投递，接口必须**幂等**，而不是"小心不要重复"。
- 幂等的判定对象是**本次通知对应的支付流水**，不是被支付的订单；合并支付场景下这个区别尤其明显。
- 真相来源是**数据库唯一索引 + 状态跃迁 CAS**，不是分布式锁，也不是应用层的"先查后写"。
- 副作用与状态变更必须在**同一事务**里；处理失败要回滚并让渠道重投，不能吞掉错误、假装成功。
- 验签失败的应答不能是成功应答，否则会丢失真实支付；但应答体必须是渠道期望的结构，且要显式写回。
- 金额与币种不一致必须拒绝入账并转人工，不能按回调金额处理。
- 回调解决不了漏单，对账和对 refund / 撤销路径的所有者划分，和幂等同等重要。
